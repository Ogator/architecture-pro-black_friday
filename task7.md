## Критерии выбора шард-ключа

Для каждой коллекции ключ подбирался по четырём критериям:

1. **Кардинальность** — сколько различных значений у ключа. Она задаёт верхнюю границу
   числа чанков: ключ с десятком значений не разложить на десять шардов.
2. **Частотность** — насколько равномерно распределены значения. Один «тяжёлый» клиент
   или одна популярная категория создают горячий чанк.
3. **Монотонность** — если ключ постоянно растёт (дата, `ObjectId`), все новые вставки
   идут в чанк с максимальным диапазоном, и запись упирается в один шард.
4. **Таргетируемость операций** — попадает ли ключ (или его префикс) в фильтр частых
   запросов. Если нет, `mongos` рассылает запрос на все шарды (scatter-gather).

Первые три критерия отвечают за равномерность, четвёртый — за скорость чтения, и они
конфликтуют между собой. Ниже для каждой коллекции показано, чем именно пришлось
пожертвовать.

## Коллекция products

### Схема документа

```javascript
{
  _id: ObjectId("..."),
  category: "electronics",          // категория товара
  name: "Смартфон X",
  price: NumberDecimal("49990.00"),
  stock: [                          // остаток в каждой геозоне
    { geo_zone: "RU-URAL",   qty: 50 },
    { geo_zone: "RU-NORTHWEST", qty: 30 }
  ],
  attributes: {                     // дополнительные атрибуты
    color: "black",
    size: "6.7\""
  },
  updated_at: ISODate("2026-09-14T10:00:00Z")
}
```

### Кандидаты в шард-ключи

| Кандидат | Распределение | Таргетируемость | Вывод |
|---|---|---|---|
| `{ _id: "hashed" }` | идеально равномерное | поиск по категории и цене идёт на все шарды | отклонён |
| `{ category: 1 }` | плохое: категорий десятки, чанк категории неделим | поиск по категории точечный | отклонён |
| `{ price: 1 }` | среднее, но цена изменяемая | фильтр по цене точечный | отклонён |
| `{ category: 1, _id: 1 }` | приемлемое | категория + карточка товара точечно | **выбран** |

`{ category: 1 }` в одиночку не годится принципиально: количество чанков не может
превысить количество различных значений ключа, и чанк одной категории останется
неделимым (jumbo chunk), сколько бы товаров в неё ни попало.

`price` отклонена ещё и потому, что это изменяемое поле. Менять значение шард-ключа
в документе можно, но такая операция требует транзакции или retryable write и может
повлечь миграцию документа между шардами — для регулярной переоценки товаров это
лишние накладные расходы.

### Выбранная стратегия: ranged по `{ category: 1, _id: 1 }`

Диапазонное (ranged) шардирование, потому что главный сценарий чтения — «показать
товары категории с фильтром по цене» — это запрос по диапазону, и его нужно
направить на минимальное число шардов.

Почему подходит:

- **Кардинальность** обеспечивает `_id`: внутри категории ключ уникален, чанки делятся
  сколь угодно мелко, jumbo-чанков не возникает.
- **Поиск по категории таргетируется** префиксом ключа — `mongos` идёт только на те
  шарды, где лежит эта категория, а не опрашивает весь кластер.
- **Карточка товара** читается по `{ category, _id }` — точечный запрос на один шард.
- **Обновление остатков** тоже точечное при условии, что в запрос передаётся категория.
  Это требование к приложению: в позиции заказа нужно хранить `category` рядом с
  `product_id` (см. схему `orders` ниже), иначе обновление по одному `_id` превратится
  в broadcast на все шарды.

Чем пожертвовали: запись новых товаров в одну популярную категорию концентрируется
в её диапазоне. Для каталога это приемлемо — товары заводят редко, а основная
нагрузка на запись здесь это обновление остатков, которое распределено по всем
существующим товарам.

```javascript
sh.shardCollection("shop.products", { category: 1, _id: 1 });

// индексы под частые операции
db.products.createIndex({ category: 1, price: 1 });      // фильтр по диапазону цен
db.products.createIndex({ "stock.geo_zone": 1 });        // наличие в геозоне
db.products.createIndex({ price: 1 });                   // сквозной фильтр по всему каталогу
```

### Как отрабатывает фильтр по цене

Поведение зависит от того, есть ли в фильтре категория. Условия замера:

- 20000 товаров, пять категорий, разведённых по двум шардам;
- **цены в документах** распределены равномерно в диапазоне от `100` до `100 000`;
- **диапазон поиска** — `price: { $gte: 1000, $lte: 2000 }`, то есть около 1 % каталога.

Под такой фильтр попадает 190 документов из 20000 по всему каталогу, из них 36 — внутри
категории `electronics`. Отсюда два разных значения в колонке «Вернулось»: запрос с
категорией ищет только внутри неё и отдаёт 36, запрос без категории — 190 по всему
каталогу. Сравнивать строки между собой нужно по колонке «Прочитано док.» — она
показывает, какой ценой найден этот результат:

| Запрос | Стадия | Шардов | Индекс | Прочитано док. | Вернулось |
|---|---|---|---|---|---|
| `{ category, price: {$gte,$lte} }` | `SINGLE_SHARD` | 1 | `category_1_price_1` | 36 | 36 |
| то же + `.sort({ price: 1 })` | `SINGLE_SHARD` | 1 | `category_1_price_1` | 36 | 36 |
| `{ price: {$gte,$lte} }` без категории | `SHARD_MERGE` | 2 | `COLLSCAN` | 20000 | 190 |
| то же, но с индексом `{ price: 1 }` | `SHARD_MERGE` | 2 | `price_1` | 190 | 190 |

**С категорией** запрос попадает в лучший случай: префикс `category` направляет его на
один шард, составной индекс отрабатывает диапазон цен, прочитано ровно столько
документов, сколько вернулось. Сортировка по цене при этом бесплатна — индекс уже
хранит значения упорядоченными, отдельной стадии `SORT` не возникает.

**Без категории** запрос деградирует дважды: рассылается на все шарды и на каждом
вырождается в `COLLSCAN`, потому что по составному индексу `{ category: 1, price: 1 }`
нельзя взять диапазон, не зная значения первого поля. Прочитано 20000 документов
ради 190.

Поэтому в набор индексов добавлен отдельный `{ price: 1 }`. Рассылку на все шарды он
не убирает — цена не входит в шард-ключ, — но превращает полное сканирование в точное
попадание по индексу: 190 прочитанных документов вместо 20000.

Для магазина это приемлемый баланс: витрина всегда открывается внутри категории, и
основной сценарий работает по первому варианту. Сквозной фильтр по цене по всему
каталогу — редкая операция, и её обслуживает `{ price: 1 }`.

## Коллекция orders

### Схема документа

```javascript
{
  _id: ObjectId("..."),
  customer_id: "c-10045",
  created_at: ISODate("2026-09-14T10:15:00Z"),
  status: "paid",                   // created | paid | shipped | delivered | cancelled
  geo_zone: "RU-CENTER",            // геозона заказа
  total: NumberDecimal("53980.00"),
  items: [
    {
      product_id: ObjectId("..."),
      category: "electronics",      // дублируем ради точечного списания остатка
      name: "Смартфон X",           // снимок на момент заказа
      price: NumberDecimal("49990.00"),
      qty: 1
    }
  ]
}
```

Цена и название товара сохраняются снимком в позиции заказа: заказ обязан остаться
неизменным, даже если товар потом подорожает или будет переименован.

### Кандидаты в шард-ключи

| Кандидат | Распределение | Таргетируемость | Вывод |
|---|---|---|---|
| `{ created_at: 1 }` | худшее: монотонный рост, все вставки в один шард | история по дате точечно | отклонён |
| `{ _id: "hashed" }` | идеально равномерное | история клиента — broadcast | отклонён |
| `{ customer_id: 1 }` | зависит от формата id, возможна монотонность | история точечно | отклонён |
| `{ customer_id: "hashed", _id: 1 }` | равномерное | история точечно | **выбран** |

`created_at` — классический антипаттерн. Заказы создаются «сейчас», поэтому все
вставки попадают в чанк с максимальным диапазоном, и вся запись ложится на один шард.

### Выбранная стратегия: составной hashed-ключ `{ customer_id: "hashed", _id: 1 }`

Хеширование берёт на себя равномерность записи, а `customer_id` в качестве префикса —
таргетируемость истории заказов.

Почему подходит:

- **Создание заказов распределяется равномерно.** Хеш `customer_id` «размазывает»
  одновременные заказы разных клиентов по всем шардам — пиковая нагрузка распродажи
  делится между шардами, а не концентрируется на одном.
- **История заказов клиента точечная.** Запрос `{ customer_id: "c-10045" }` содержит
  префикс ключа, поэтому идёт на один шард, а не на весь кластер.
- **Все заказы клиента лежат рядом**, что делает выборку истории дешёвой.
- **Второе поле `_id` даёт делимость.** Это важно: на чистом `{ customer_id: "hashed" }`
  все заказы одного клиента попадают в одно значение хеша, и чанк оптового покупателя
  стал бы неделимым. Составной hashed-ключ (одно хешированное поле плюс обычные)
  снимает проблему.

Чем пожертвовали: показ статуса заказа по одному `_id` будет broadcast-запросом,
так как `_id` не префикс ключа. Решается на уровне приложения — статус смотрит
владелец заказа, его `customer_id` известен из сессии, поэтому запрос строится как
`{ customer_id, _id }` и остаётся точечным.

```javascript
sh.shardCollection("shop.orders", { customer_id: "hashed", _id: 1 });

db.orders.createIndex({ customer_id: 1, created_at: -1 });  // история, свежие сверху
db.orders.createIndex({ status: 1, created_at: -1 });       // выборки для операционных задач
```

### Альтернатива: зональное шардирование по геозоне

Если появится требование держать заказы региона физически ближе к его пользователям
(или соблюдать требования к месту хранения данных), геозона должна войти в шард-ключ:
зональные диапазоны строятся **только по префиксу шард-ключа**, по полю вне ключа
диапазон задать нельзя.

```javascript
sh.shardCollection("shop.orders", { geo_zone: 1, customer_id: 1, _id: 1 });

sh.addShardToZone("shard1", "CENTER");
sh.addShardToZone("shard2", "URAL");

sh.updateZoneKeyRange(
  "shop.orders",
  { geo_zone: "RU-CENTER", customer_id: MinKey, _id: MinKey },
  { geo_zone: "RU-CENTER", customer_id: MaxKey, _id: MaxKey },
  "CENTER"
);
sh.updateZoneKeyRange(
  "shop.orders",
  { geo_zone: "RU-URAL", customer_id: MinKey, _id: MinKey },
  { geo_zone: "RU-URAL", customer_id: MaxKey, _id: MaxKey },
  "URAL"
);
```

Плата за это — неравномерность: Москва даст кратно больше заказов, чем малонаселённый
регион, и шард зоны `CENTER` будет нагружен сильнее. Поэтому по умолчанию выбран
вариант с хешем, а зональный — только если появится требование локальности.

### Альтернатива: геозона + хеш внутри зоны

У чисто зонального варианта есть слабое место: как только зона получает больше одного
шарда, `{ geo_zone: 1, customer_id: 1, _id: 1 }` всё равно раскладывает заказы клиентов
по порядку `customer_id`, а не равномерно. Это ограничение можно снять, не добавляя
«второй уровень» шардирования — в MongoDB его и нет, у коллекции всегда один шард-ключ
и одна общая карта чанков, — а хешируя `customer_id` прямо внутри того же составного
ключа. Начиная с MongoDB 4.4 хешированным может быть любое одно поле составного ключа,
не только первое, поэтому оно не обязано конфликтовать с `geo_zone` на позиции лидера:

```javascript
sh.shardCollection("shop.orders", { geo_zone: 1, customer_id: "hashed", _id: 1 });
```

`geo_zone` остаётся первым (ranged) полем — именно оно участвует в `updateZoneKeyRange`
и определяет, на каком наборе шардов вообще может лежать документ. `customer_id`
хеширован — внутри диапазона одной зоны чанки режутся по хешу и балансировщик
раскладывает их равномерно между шардами, назначенными на эту зону. `_id` по-прежнему
нужен, чтобы заказы одного клиента не схлопывались в один неделимый чанк.

Настройка зон не меняется по форме — только теперь в каждой зоне стоит держать больше
одного шарда, иначе хешировать внутри зоны нечего:

```javascript
sh.addShardToZone("shard1a", "CENTER");
sh.addShardToZone("shard1b", "CENTER");   // второй шард той же зоны — иначе хеш бесполезен
sh.addShardToZone("shard2a", "URAL");
sh.addShardToZone("shard2b", "URAL");

sh.updateZoneKeyRange(
  "shop.orders",
  { geo_zone: "RU-CENTER", customer_id: MinKey, _id: MinKey },
  { geo_zone: "RU-CENTER", customer_id: MaxKey, _id: MaxKey },
  "CENTER"
);
sh.updateZoneKeyRange(
  "shop.orders",
  { geo_zone: "RU-URAL", customer_id: MinKey, _id: MinKey },
  { geo_zone: "RU-URAL", customer_id: MaxKey, _id: MaxKey },
  "URAL"
);
```

Границы для хешированного поля по-прежнему задаются только `MinKey`/`MaxKey` — у хеша
нет осмысленного «от-до», диапазон закрывает всё поле целиком.

Чем пожертвовали:

- **Точечный запрос по одному `customer_id` больше не работает без `geo_zone`.** В
  базовом варианте (`{ customer_id: "hashed", _id: 1 }`) фильтр `{ customer_id }` сам
  таргетируем. Здесь лидирующее поле — `geo_zone`, и без него роутер не знает, в какой
  диапазон смотреть, — запрос уходит broadcast'ом, даже с хешем на `customer_id`. На
  практике это не новая проблема: раз данные физически привязаны к регионам,
  приложение обязано знать `geo_zone` клиента, иначе смысла во всей затее нет.
- **Неравномерность между зонами никуда не уходит.** Хеш выравнивает нагрузку только
  *внутри* зоны — Москва всё так же даст кратно больше заказов, чем малонаселённый
  регион, просто теперь этот избыток можно размазать по нескольким шардам зоны, а не
  упереть в один.

Вариант оправдан, если зональное требование по локальности встаёт одновременно с
нагрузкой, которую один шард на зону не тянет: тогда `geo_zone` держит требование к
размещению, а хеш внутри — то же равномерное распределение записи, что и в базовом
решении.

## Коллекция carts

### Схема документа

Ключевая особенность: корзину ищут **по двум разным полям** — `session_id` у гостя и
`user_id` у авторизованного пользователя. Один шард-ключ не может быть префиксом обоих
фильтров сразу, поэтому в схему вводится вычисляемое поле `cart_key`.

```javascript
{
  _id: ObjectId("..."),
  cart_key: "sess:9f2c...",   // session_id гостя ИЛИ user_id пользователя
  user_id: "c-10045",         // null у гостевой корзины
  session_id: "9f2c...",      // null у пользовательской корзины
  status: "active",           // active | ordered | abandoned
  items: [
    { product_id: ObjectId("..."), quantity: 2 }
  ],
  created_at: ISODate("2026-09-14T10:00:00Z"),
  updated_at: ISODate("2026-09-14T10:05:00Z"),
  expires_at: ISODate("2026-09-21T10:05:00Z")   // TTL
}
```

`cart_key` заполняется приложением по правилу: `"sess:" + session_id` для гостя,
`"user:" + user_id` для авторизованного. Поле всегда заполнено — это обязательное
требование, так как шард-ключ должен присутствовать в каждом документе.

### Кандидаты в шард-ключи

| Кандидат | Распределение | Таргетируемость | Вывод |
|---|---|---|---|
| `{ _id: "hashed" }` | идеально равномерное | оба сценария поиска — broadcast | отклонён |
| `{ session_id: "hashed" }` | у пользовательских корзин поле пустое → все `null` в один чанк | только гостевой поиск | отклонён |
| `{ user_id: "hashed" }` | зеркальная проблема с гостевыми | только пользовательский поиск | отклонён |
| `{ cart_key: "hashed" }` | равномерное | оба сценария точечно | **выбран** |

Отдельно отмечу ловушку с `session_id`: уникальный индекс и хеш трактуют отсутствующее
поле как `null`, поэтому **все** пользовательские корзины получили бы один и тот же хеш
и легли в один чанк — гарантированная горячая точка.

### Выбранная стратегия: hashed по `{ cart_key: "hashed" }`

Почему подходит:

- **Оба сценария чтения точечные.** И `{ cart_key: "sess:...", status: "active" }`, и
  `{ cart_key: "user:...", status: "active" }` содержат шард-ключ и идут на один шард.
- **Запись распределяется равномерно.** Корзины создаются постоянно и в большом
  количестве; хеш случайных идентификаторов даёт ровное распределение без горячих точек.
- **Кардинальность максимальная** — по сути одно значение на корзину.
- **Изменения корзины дешёвые.** Добавление, замена и удаление товара — это обновление
  одного документа на одном шарде, без распределённой транзакции.
- **Очистка корзин распределена.** TTL-индекс работает независимо на каждом шарде,
  поэтому удаление протухших корзин не создаёт нагрузку на один узел.

Чем пожертвовали: слияние гостевой корзины в пользовательскую затрагивает два
документа с разными `cart_key`, которые почти наверняка лежат на разных шардах.
Это распределённая транзакция — дороже локальной, но операция происходит один раз
за логин, так что цена приемлема.

```javascript
sh.shardCollection("shop.carts", { cart_key: "hashed" });

// TTL: документ удаляется в момент, указанный в expires_at
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });

// поиск активной корзины; он же держит инвариант «одна активная корзина»
// (см. раздел «Уникальность активной корзины» ниже)
db.carts.createIndex(
  { cart_key: 1, status: 1 },
  { unique: true, partialFilterExpression: { status: "active" } }
);
```

Слияние гостевой корзины в пользовательскую:

```javascript
const session = db.getMongo().startSession();
session.withTransaction(() => {
  const carts = session.getDatabase("shop").carts;

  const guest = carts.findOne({ cart_key: "sess:9f2c...", status: "active" });
  if (!guest) return;

  carts.updateOne(
    { cart_key: "user:c-10045", status: "active" },
    {
      $push: { items: { $each: guest.items } },
      $currentDate: { updated_at: true }
    },
    { upsert: true }
  );

  carts.updateOne(
    { _id: guest._id },
    { $set: { status: "abandoned" }, $currentDate: { updated_at: true } }
  );
});
session.endSession();
```

### Уникальность активной корзины

Инвариант «у одного `cart_key` не больше одной активной корзины» с hashed-ключом
выполним, но не любым индексом. Поведение проверено на кластере:

| Индекс | Результат |
|---|---|
| `{ cart_key: "hashed" }` с `unique: true` | отклонён, `Location16764` |
| `{ cart_key: 1 }` с `unique: true` | создаётся, дубликат отклоняется с `E11000` |
| `{ session_id: 1 }` с `unique: true` | отклонён, `CannotCreateIndex` — поле вне шард-ключа |
| `{ cart_key: 1, status: 1 }`, `unique` + `partialFilterExpression` | создаётся и работает |

Логика правила такая: уникальность в шардированной коллекции MongoDB обеспечивает
только тогда, когда одинаковые значения ключа гарантированно лежат на одном шарде.
При хешировании по `cart_key` все документы с одним и тем же `cart_key` дают один хеш
и попадают в один чанк, поэтому локальной проверки на шарде достаточно — отдельный
ranged-индекс по тому же полю разрешён. Для поля вне шард-ключа (`session_id`) такой
гарантии нет, и индекс отклоняется. А сам hashed-индекс уникальным сделать нельзя:
хеш не восстанавливает исходное значение, и коллизия двух разных значений выглядела бы
как нарушение уникальности.

Рекомендуемый вариант — частичный уникальный индекс:

```javascript
db.carts.createIndex(
  { cart_key: 1, status: 1 },
  { unique: true, partialFilterExpression: { status: "active" } }
);
```

Он разрешает у одного `cart_key` сколько угодно корзин в статусах `ordered` и
`abandoned` (это история) и ровно одну в статусе `active`. Ограничение при этом
держит база, а не код приложения.

## Сводная таблица

| Коллекция | Шард-ключ | Стратегия | Главный аргумент |
|---|---|---|---|
| `products` | `{ category: 1, _id: 1 }` | ranged | поиск по категории и диапазону цен таргетируется префиксом ключа |
| `orders` | `{ customer_id: "hashed", _id: 1 }` | hashed (составной) | равномерная запись в пик распродажи + точечная история клиента |
| `carts` | `{ cart_key: "hashed" }` | hashed | единый ключ делает точечными оба сценария поиска корзины |

## Полный скрипт инициализации

```javascript
sh.enableSharding("shop");

// --- products: ranged ---
sh.shardCollection("shop.products", { category: 1, _id: 1 });
db.products.createIndex({ category: 1, price: 1 });
db.products.createIndex({ "stock.geo_zone": 1 });
db.products.createIndex({ price: 1 });

// --- orders: составной hashed ---
sh.shardCollection("shop.orders", { customer_id: "hashed", _id: 1 });
db.orders.createIndex({ customer_id: 1, created_at: -1 });
db.orders.createIndex({ status: 1, created_at: -1 });

// --- carts: hashed + TTL ---
sh.shardCollection("shop.carts", { cart_key: "hashed" });
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });
db.carts.createIndex(
  { cart_key: 1, status: 1 },
  { unique: true, partialFilterExpression: { status: "active" } }
);

// --- проверка ---
sh.status();
db.orders.getShardDistribution();
```

## Ограничения, которые учитывались

Решения выше опираются на следующие свойства шардирования в MongoDB:

- **Зональные диапазоны задаются только по префиксу шард-ключа.** Поле, по которому
  нужно разложить данные географически, обязано входить в шард-ключ — поэтому
  зональный вариант для `orders` потребовал `geo_zone` первым полем.
- **Уникальный индекс должен начинаться с поля шард-ключа.** Индекс по полю вне ключа
  отклоняется (`CannotCreateIndex`). Сам hashed-индекс уникальным сделать нельзя
  (`Location16764`), но отдельный ranged-индекс по тому же полю — можно, и уникальность
  он действительно обеспечивает, потому что при хешировании равные значения всегда
  оказываются на одном шарде.
- **Хеширование — штатное решение для монотонно растущих значений** (`created_at`,
  `ObjectId`), но само по себе равномерности не гарантирует: кардинальность и
  частотность значений влияют не меньше.
- **Составной hashed-ключ допускает ровно одно хешированное поле**, остальные — обычные.
  Это то, что позволило совместить равномерность по `customer_id` с делимостью по `_id`.
- **`expireAfterSeconds` принимает целое число от 0 до 2147483647.** Значение `0`
  означает «удалить в момент, указанный в самом поле» — именно этот режим нужен
  для `expires_at`.
