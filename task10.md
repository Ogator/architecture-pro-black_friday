## 10.1. Какие данные критичны и где Cassandra оправдана

Критичность оценивается по двум независимым осям — **целостность** (нельзя потерять
или задвоить запись, нельзя разойтись в двух копиях) и **скорость обработки под
экстремальной нагрузкой** (пик распродажи, 50 000 RPS, пиковая запись, а не чтение).
Cassandra оправдана там, где вторая ось доминирует: leaderless-репликация и
consistent hashing дают почти линейное масштабирование записи без остановки
кластера на rebalance.

| Данные | Объём записи в пик | Природа данных | Нужна ли строгая транзакционность | Геораспределённость | Вывод |
|---|---|---|---|---|---|
| `orders` (создание, смена статуса) | очень высокий, всплесками | append-heavy, почти неизменяемые после создания | точечная (идемпотентность платежа, см. [задание 9](./task9.md#коллекция-orders)), не межколлекционная | да, нужен показ «своих» заказов быстро из ближайшего ЦОД | **переносится** — запись, а не сложные ad-hoc запросы |
| `carts` | очень высокий, почти на каждое действие пользователя | эфемерные, TTL, одна запись = один партиционный ключ | нет (см. [задание 7](./task7.md#коллекция-carts): слияние — исключение, а не типовой путь) | да, локальная сессия пользователя | **переносится** — тот профиль, для которого Cassandra проектировалась |
| пользовательские сессии | очень высокий | эфемерные, TTL, ключ-значение по `session_id` | нет | да | **переносится** — TTL нативно поддержан на уровне строки |
| история заказов (архив для отчётности) | низкий (batch) | append-only, читается пачками | нет | нет, читается back-office | **переносится вместе с orders** — тот же append-only паттерн, витрина отчётности через тот же набор таблиц |
| `products` (каталог, остатки, цена) | низкий по числу товаров, но **высокая конкурентность записи на один документ** (хайповый SKU) | изменяемое состояние, конкурентная запись в одну и ту же строку | **да** — атомарное условное списание остатка | нет, каталог общий | **не переносится**, см. [обоснование](#что-осознанно-не-переносится-products) |

Формально задание перечисляет «заказы, товары, корзины, история заказов,
пользовательские сессии» как кандидатов — из них в Cassandra переезжают все, кроме
`products`. Общий признак четырёх перенесённых сущностей: под нагрузкой они **пишутся**,
а не конкурентно **изменяются** одной и той же строкой, и почти всегда читаются по
известному ключу (`order_id`, `customer_id`, `cart_key`, `session_id`), а не
произвольным диапазоном или вторичным условием (диапазон цены, поиск по атрибуту) —
именно под такой профиль доступа Cassandra и проектируется: партиционирование должно
знать ключ запроса заранее (query-first data modeling), а не наоборот.

## 10.2. Концептуальная модель

Общий принцип Cassandra, определяющий все ключи ниже: **одна таблица — один паттерн
запроса**. В отличие от MongoDB, где `orders` — одна коллекция с разными индексами под
разные фильтры ([задание 7](./task7.md#коллекция-orders)), в Cassandra под каждый
паттерн чтения заводится отдельная денормализованная таблица, и согласованность между
ними — забота приложения (batch на запись), а не базы.

### orders_by_id

Точечный доступ по идентификатору заказа: подтверждение сразу после оформления,
идемпотентность платёжного вебхука, операционный check-then-act по статусу —
все три операции в [задании 9](./task9.md#коллекция-orders) требовали PRIMARY-эквивалентной
свежести именно по `order_id`.

```sql
CREATE TABLE shop.orders_by_id (
    order_id      uuid,
    customer_id   text,
    status        text,       -- created | paid | shipped | delivered | cancelled
    geo_zone      text,
    total         decimal,
    items         list<frozen<order_item>>,
    created_at    timestamp,
    updated_at    timestamp,
    payment_id    text,       -- идемпотентность вебхука
    PRIMARY KEY (order_id)
);
```

**Partition key `order_id`.** UUID (аналог `ObjectId` в MongoDB) равномерно
распределяется хешем по кольцу — ни одно значение не создаёт более тяжёлую партицию,
чем другое, в отличие от `created_at`, который в MongoDB был явно отклонён как
шард-ключ ([задание 7](./task7.md#кандидаты-в-шард-ключи)) именно из-за монотонности.
Кластерных ключей нет — партиция содержит ровно одну строку, запрос по `order_id`
всегда попадает на один узел (координатор идёт напрямую в нужную партицию по кольцу),
без broadcast-эффекта, который в MongoDB возникал у нетаргетируемых запросов.

Смена статуса — `UPDATE ... WHERE order_id = ?`, точечная запись в ту же партицию.
Для идемпотентности платежа используется **lightweight transaction** (Paxos,
условная запись):

```sql
UPDATE shop.orders_by_id
SET status = 'paid', updated_at = toTimestamp(now())
WHERE order_id = ?
IF payment_id != ?;
```

LWT здесь оправдан: партиция одна (конкретный заказ), конкуренция за неё
кратковременная (один вебхук вряд ли дублируется параллельно тысячи раз на один и
тот же заказ) — в отличие от каталога, где такая же техника на хайповом SKU стала бы
узким местом (см. [ниже](#что-осознанно-не-переносится-products)).

### orders_by_customer

Личный кабинет — история заказов клиента, отсортированная по свежести:

```sql
CREATE TABLE shop.orders_by_customer (
    customer_id   text,
    created_at    timestamp,
    order_id      uuid,
    status        text,
    total         decimal,
    PRIMARY KEY (customer_id, created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id DESC);
```

**Partition key `customer_id`, кластерные ключи `created_at, order_id`.** Тот же
выбор, что и составной hashed-ключ в MongoDB
([задание 7](./task7.md#выбранная-стратегия-составной-hashed-ключ-customer_id-hashed-_id-1)):
все заказы клиента физически рядом (одна партиция), запрос истории — один диапазонный
скан внутри партиции без чтения чужих данных, а `_id`/`order_id` вторым/третьим
ключом даёт делимость — партиция клиента не может «слипнуться» в одну неделимую
запись. `created_at DESC` в порядке кластеризации означает, что «последние заказы
сверху» отдаются без отдельной сортировки на чтении.

Разница с MongoDB — не в идее ключа, а в цене денормализации: обновление статуса
заказа требует записи **в обе** таблицы (`orders_by_id` и `orders_by_customer`),
и Cassandra не даёт транзакции между партициями — используется `BATCH` в пределах
одного логического изменения:

```sql
BEGIN BATCH
  UPDATE shop.orders_by_id       SET status = 'paid' WHERE order_id = ?;
  UPDATE shop.orders_by_customer SET status = 'paid' WHERE customer_id = ? AND created_at = ? AND order_id = ?;
APPLY BATCH;
```

`BATCH` в Cassandra — не ACID-транзакция в смысле MongoDB, а гарантия «в конце концов
применится к обеим партициям» (через log-batch на координаторе с ретраем); в паре с
LWT на `orders_by_id` для критичного пути (идемпотентность платежа) это осознанный
компромисс — сильная гарантия там, где бизнес-риск велик, и более мягкая там, где
временное рассогласование историй чтения не критично (`orders_by_customer` —
read-путь, покрытый допустимым отставанием ещё в [задании 9](./task9.md#коллекция-orders)).

**Горячие партиции.** У обычного покупателя партиция маленькая и не растёт быстро.
Риск — B2B-клиент с тысячами заказов в день в пик распродажи: партиция одного
`customer_id` становится непропорционально большой и горячей на запись (все его
заказы всегда идут в одну и ту же партицию — прямой аналог перекоса по нагрузке из
[задания 8](./task8.md#как-возникает-горячий-шард-на-этих-данных), только на уровне
Cassandra-партиции, а не MongoDB-чанка). Митигация — та же идея, что zone sharding
там: искусственно расширить кардинальность бакетом по времени в составе partition key:

```sql
PRIMARY KEY ((customer_id, month_bucket), created_at, order_id)
```

где `month_bucket = '2026-11'`. Для 99% клиентов это не нужно (партиция и так мала),
для аномально активных — ограничивает размер партиции сверху без изменения формы
запроса (история всё так же читается диапазонным сканом, просто по известным
бакетам). Применяется точечно, тем же принципом «не для всех, а для подтверждённо
горячих», что и суффикс-партиционирование остатков в задании 8.

**Резидентность (`geo_zone`).** Если потребуется физически держать заказы региона
ближе к пользователям (как в зональной альтернативе [задания 7](./task7.md#альтернатива-зональное-шардирование-по-геозоне)),
это решается не ключом, а `NetworkTopologyStrategy` — привязкой репликации к
датацентру на уровне keyspace, а не отдельной таблицей.

### carts

```sql
CREATE TABLE shop.carts (
    cart_key    text,
    user_id     text,
    session_id  text,
    status      text,
    items       list<frozen<cart_item>>,
    updated_at  timestamp,
    PRIMARY KEY (cart_key)
) WITH default_time_to_live = 604800; -- 7 суток, как expires_at в MongoDB
```

**Partition key `cart_key`** — переносится один в один: то же вычисляемое поле
(`"sess:" + session_id` / `"user:" + user_id`), что уже решило проблему «поиск по
двум разным полям» в [задании 7](./task7.md#коллекция-carts). Партиция — одна строка,
запись «добавить товар» и чтение «показать корзину» всегда попадают на одну и ту же
партицию и одну и ту же реплику по кольцу — никакого broadcast.

TTL здесь — не отдельный индекс с фоновой job'ой, как в MongoDB
(`expireAfterSeconds`, задание 7), а нативное свойство строки в Cassandra: узел
физически не отдаёт просроченную запись при чтении и удаляет её compaction'ом
самостоятельно, без централизованного TTL-монитора.

Слияние гостевой корзины в пользовательскую при логине — то же ограничение, что и
`orders`: две разные партиции (`sess:...` и `user:...`), нет кросс-партиционной
транзакции, поэтому `BATCH` из двух условных записей вместо MongoDB-сессии с
`withTransaction`.

### sessions

```sql
CREATE TABLE shop.sessions (
    session_id  text,
    customer_id text,
    payload     text,          -- сериализованное состояние сессии
    created_at  timestamp,
    PRIMARY KEY (session_id)
) WITH default_time_to_live = 86400; -- 24 часа
```

Простейший случай — чистый key-value по случайному `session_id`, равномерное
распределение гарантировано самой природой ключа, TTL решает очистку так же, как у
`carts`.

### Что осознанно НЕ переносится: products

Два свойства `products`, которые в MongoDB решались шард-ключом и составным
индексом ([задание 7](./task7.md#коллекция-products)) и режимом чтения PRIMARY
([задание 9](./task9.md#коллекция-products)), в Cassandra стоят дорого одновременно:

1. **Диапазонный запрос по цене внутри категории** (`{ category, price: {$gte,$lte} }`)
   — в Cassandra эффективен только диапазон по **кластерному** ключу внутри
   партиции. Чтобы `price` был диапазонным внутри `category`, пришлось бы сделать
   `category` партиционным ключом — и вернуться к тому же перекосу, который в
   MongoDB был явно отклонён («категорий десятки, чанк категории неделим», задание 7):
   в Cassandra партиция `category: "electronics"` точно так же станет неограниченно
   растущей и горячей, а решардинга, ослабляющего именно эту проблему, Cassandra не
   даёт — переразбиение партиции по ключу нельзя сделать без изменения модели и
   перезаписи данных.
2. **Атомарное условное списание остатка под конкуренцией на одном SKU.** Единственный
   инструмент Cassandra для «списать, если остаток достаточен» — LWT (`UPDATE ... IF
   qty >= ?`), который на **каждую** запись в партицию прогоняет Paxos-раунд (round-trip
   для prepare+propose+commit по кворуму реплик) и тем самым сериализует запись в эту
   партицию. Для обычного заказа это приемлемая цена, но именно на хайповом SKU в пик
   распродажи — том самом сценарии, где 70% трафика идёт в одну категорию
   ([задание 8](./task8.md#как-возникает-горячий-шард-на-этих-данных)) — LWT превращает
   и без того горячую партицию в последовательную очередь Paxos-раундов: то же самое
   узкое место, которое переезд на Cassandra должен был устранить, воспроизводится
   заново на уровне одной партиции.

Каталог остаётся в MongoDB, где ranged-шардирование по `{ category, _id }` уже
таргетирует диапазон цены индексом, а атомарное списание — обычный `findOneAndUpdate`
без распределённого консенсуса поверх одной строки. Cassandra в этой архитектуре
берёт на себя ту часть нагрузки, где она выигрывает: запись большого потока
независимых событий (заказы, корзины, сессии) с ключом, известным заранее.

## 10.3. Hinted Handoff, Read Repair, Anti-Entropy Repair

Три механизма решают разные по природе расхождения между репликами, и выбор между
ними — не взаимоисключающий, а вопрос **интенсивности**: насколько агрессивно каждый
из них включён для конкретной таблицы.

- **Hinted Handoff** — координатор запоминает несостоявшуюся запись на недоступный узел
  и доигрывает её, когда узел вернётся (в пределах `max_hint_window`, по умолчанию 3
  часа). Дёшево, работает в фоне, не добавляет latency операции на клиенте.
- **Read Repair** — при чтении с consistency level выше `ONE` координатор сверяет
  ответы нескольких реплик и на месте чинит расхождение у той, что отстала. Стоит
  дополнительного round-trip'а на чтении (или выполняется асинхронно после ответа
  клиенту, в зависимости от настройки), но не требует отдельного окна обслуживания.
- **Anti-Entropy Repair** (`nodetool repair`) — полное сравнение данных между
  репликами через дерево Меркла и досылка разницы. Самый тяжёлый механизм: нагружает
  диск и сеть на время выполнения, поэтому по аналогии с окном балансировщика
  MongoDB ([задание 8](./task8.md#1-штатный-балансировщик-чанков--необходимое-но-не-достаточное-условие))
  запускается по расписанию вне пиковой нагрузки, а не во время самой распродажи.
  Единственный механизм, гарантированно закрывающий расхождение, которое пережило
  `max_hint_window` (узел был недоступен дольше 3 часов) — Hinted Handoff в этом
  случае просто теряет накопленные хинты.

| Сущность | Consistency level (запись / чтение) | Hinted Handoff | Read Repair | Anti-Entropy Repair | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
|---|---|---|---|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `orders_by_id`, `orders_by_customer` | `LOCAL_QUORUM` / `LOCAL_QUORUM` | да | включён (`read_repair_chance` на уровне default для быстрых consistency-конфликтов) | по расписанию, регулярно (например, еженедельно, вне пика) | деньги и статус заказа — как и в [задании 9](./task9.md#коллекция-orders), устаревшее или расходящееся значение здесь не «немного неточная витрина», а риск задвоить оплату или отменить уже отгруженный заказ. `LOCAL_QUORUM` на чтении и записи даёт `R + W > RF` — строгую консистентность в пределах ЦОД без broadcast на все реплики. Anti-entropy обязателен по расписанию: это финансово значимые данные, которые не должны разойтись перманентно, даже если узел был недоступен дольше окна хинтов |
| `carts` | `LOCAL_QUORUM` / `LOCAL_ONE` | да | включён с низкой вероятностью | опционально, редко (данные короткоживущие, TTL сам чистит расхождение) | запись — та же цена, что у заказов (потеря товара из корзины заметна пользователю, см. read-your-writes в [задании 9](./task9.md#проблема-read-your-writes-и-как-она-решена)), но чтение можно ослабить до `LOCAL_ONE`: минорное расхождение по составу корзины не бизнес-критично и следующий же read repair на GET его подчистит. TTL 7 дней снимает необходимость агрессивного anti-entropy — устаревшая копия просто истечёт сама                                                                      |
| `sessions` | `LOCAL_ONE` / `LOCAL_ONE` | да | выключен или минимальная вероятность | нет | чисто ключ-значение, TTL 24 часа, повторный логин переписывает запись целиком — цена временной рассинхронизации ниже цены дополнительной latency на каждый запрос сессии при 50 000 RPS. Anti-entropy не нужен: любое расхождение живёт не дольше TTL                                                                                                                                                                                                                                                      |

**Логика распределения.**
Чем выше цена ошибки (деньги, риск повторной обработки, видимая пользователю потеря
данных «прямо сейчас»), тем выше consistency level и тем агрессивнее repair-механизмы,
вплоть до регулярного anti-entropy для `orders`. Чем эфемернее и дешевле неточность
(`sessions`, отчасти `carts`), тем сильнее приоритет отдаётся latency под пиковой
нагрузкой — `LOCAL_ONE` и минимум фоновой работы. Hinted Handoff включён для всех трёх
без исключения: это самый дешёвый механизм, а его отсутствие означает, что любой
временный сбой узла в пик распродажи гарантированно требует anti-entropy-догонки
позже — платить чуть-чуть постоянно дешевле, чем платить много редко, но во время
уже понесённого сбоя.
