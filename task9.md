## Как читает приложение: readPreference и его границы

Приложение `pymongo_api` подключается только к
`mongos_router` и не знает, какой узел внутри шарда сейчас PRIMARY — режим чтения
задаётся на уровне клиента или конкретного запроса через `read_preference`:

```python
from pymongo import ReadPreference

# на весь коллекшн-хэндл
db.get_collection("products", read_preference=ReadPreference.SECONDARY_PREFERRED)

# точечно на один запрос
db.orders.find_one(
    {"customer_id": cid, "_id": oid},
    read_preference=ReadPreference.PRIMARY,
)
```

Два технических ограничения драйвера важны для чисел ниже:

- **`maxStalenessSeconds` не может быть меньше 90 секунд** — это ограничение спецификации
  MongoDB-драйверов (`max(90, heartbeatFrequencyMS + 10s)`), а не выбор конфигурации.
  Поэтому `maxStalenessSeconds` годится только там, где допустимое отставание измеряется
  минутами; для более узких требований (единицы секунд) он бесполезен в принципе — там
  либо `PRIMARY`, либо **causal consistency** (см. ниже).
- **`SECONDARY` в шардированном кластере читает с secondary каждого опрошенного шарда
  независимо.** Если запрос из-за отсутствия шард-ключа в фильтре уходит broadcast'ом, у разных шардов
  может быть разное отставание, и результат — смесь данных разной свежести. Это
  дополнительный аргумент направлять на SECONDARY только точечные, таргетируемые запросы.

## Коллекция products

| Операция чтения | PRIMARY / SECONDARY | Допустимое отставание | Комментарий |
|---|---|---|---|
| Листинг каталога по категории + фильтр по цене (витрина) | **SECONDARY** (`secondaryPreferred`) | до 5–10 c в норме, до ~30 c в пик распродажи | витрина открывается внутри категории — таргетируемый запрос на один шард; |
| Карточка товара (`{ category, _id }`) | **SECONDARY** (`secondaryPreferred`) | до 5–10 c | то же обоснование, точечный запрос |
| Проверка наличия при показе карточки/в списке (`stock.geo_zone`) | **SECONDARY** | до 5–10 c | показ индикатора «в наличии» — не резервирование; ложноположительный «в наличии» на устаревшей реплике допустим, следующий шаг (добавление в корзину/оформление) перепроверит актуальный остаток |
| Проверка остатка непосредственно перед списанием при оформлении заказа | **PRIMARY** | 0 (без учёта времени репликации самой записи) | здесь риск переходит в деньги: устаревший «в наличии» на SECONDARY = продажа отсутствующего товара. Списание остатка — атомарный `findOneAndUpdate` с условием `qty >= requested` на PRIMARY, а не «прочитать потом списать» |
| Цена товара в момент подтверждения заказа | **PRIMARY** | 0 | цена фиксируется снимком в `orders.items[].price`; прочитать её нужно из источника, гарантированно отражающего последнюю запись admin-панели о переоценке — иначе клиенту может достаться цена до подорожания, зафиксированная в заказе как обязательство магазина |
| Сквозной фильтр по цене по всему каталогу (редкая операция) | **SECONDARY** | до 10–30 c | нетаргетируемый broadcast-запрос; не влияет на риск продажи, просто витрина, отставание некритично |

**Почему листинг и карточка — SECONDARY.** Частота обновлений `products` низкая
относительно частоты чтения: остатки меняются пачками (продажи, приход), цена — ещё
реже, а витрину открывают на порядки чаще, чем меняют товар. Показ витрины не создаёт
обязательств — пользователь ещё ничего не купил, устаревшая на несколько секунд цена
или остаток не наносят ущерб бизнесу. Это ровно тот трафик, ради равномерного
распределения которого имеет смысл снимать нагрузку с PRIMARY на SECONDARY, особенно
в пик распродажи, когда PRIMARY каждого шарда и так обслуживает основной поток записи.

**Почему списание и цена при оформлении — PRIMARY.** Это те две операции, где
задание явно называет риск: «продажа недоступного товара» и обязательство магазина по
зафиксированной цене. Здесь недопустима не только устаревшая секунда, а сам паттерн
«прочитать на SECONDARY, потом решить о записи на PRIMARY» — между чтением и записью
кто-то другой может списать последнюю единицу. Правильная реализация — не readPreference,
а атомарная операция на PRIMARY (`findOneAndUpdate` с условием в фильтре), которая
делает отдельное чтение остатка перед списанием лишним.

## Коллекция orders

| Операция чтения | PRIMARY / SECONDARY | Допустимое отставание | Комментарий |
|---|---|---|---|
| История заказов клиента (`{ customer_id }`, личный кабинет) | **SECONDARY** (`secondaryPreferred`) | до 10–15 c | таргетируемый запрос на один шард; список старых заказов не обязан включать заказ, оформленный секунду назад |
| Страница подтверждения сразу после оформления заказа (`{ customer_id, _id }`) | **PRIMARY** (или SECONDARY + causal consistency) | 0 | классический read-your-writes: клиент только что создал заказ и должен увидеть именно его, а не «заказ не найден» из-за отставания реплики |
| Статус заказа в личном кабинете (просмотр после подтверждения) | **SECONDARY** | до 10–15 c | статус меняется нечасто (created → paid → shipped → delivered), пользователь неспособен заметить отставание в секунды между сменами статуса |
| Статус заказа для операционных задач: чтение перед сменой статуса (например, «отменить, если ещё не отгружен») | **PRIMARY** | 0 | это check-then-act: решение об отмене принимается по прочитанному статусу и сразу записывается; устаревший на SECONDARY статус «created» вместо актуального «shipped» приведёт к попытке отменить уже отгруженный заказ |
| Идемпотентность обработки платёжного вебхука (уже применён ли этот `payment_id`) | **PRIMARY** | 0 | ложноотрицательный результат на устаревшей реплике = повторное зачисление оплаты; это ровно тот случай, где «риск отображения устаревшего статуса» из задания превращается в риск задвоения бизнес-события, а не просто в UI-неточность |
| Операционные/аналитические выборки (`{ status, created_at }`, дашборд поддержки, отчёты) | **SECONDARY** | до 30–60 c | агрегированная картина, не решение по конкретному заказу; секунды отставания несущественны на фоне периода агрегации |

**Почему история — SECONDARY, а подтверждение и check-then-act — PRIMARY.** Разница не
в самой коллекции, а в том, что происходит с прочитанным значением дальше. Просмотр
истории — терминальная операция: пользователь смотрит и ничего не решает на основе
устаревшего заказа. Подтверждение после оформления и смена статуса — это тот
сценарий из задания про «риск отображения устаревшего статуса заказа пользователю»
(в момент, где эта устаревшесть максимально заметна — сразу после действия) и «принятие
решения по прочитанному значению» (отмена, идемпотентность платежа) — там устаревшесть
не заметна пользователю визуально, а ломает бизнес-инвариант.

## Коллекция carts

| Операция чтения | PRIMARY / SECONDARY | Допустимое отставание | Комментарий |
|---|---|---|---|
| Просмотр активной корзины в текущей сессии (после `add`/`update`/`remove`) | **PRIMARY** (или SECONDARY + causal consistency) | 0 | пользователь только что положил товар и должен увидеть его в корзине немедленно — read-your-writes |
| Проверка активной корзины перед слиянием при логине | **PRIMARY** | 0 | чтение — часть той же распределённой транзакции слияния; транзакции в MongoDB читают в рамках своей сессии, что фактически означает PRIMARY на затронутых шардах |
| Проверка инварианта «одна активная корзина на cart_key» перед вставкой | **PRIMARY** | 0 | де-факто обеспечивается частичным уникальным индексом на запись, но если приложение делает предварительное чтение для UX (например, чтобы не пытаться вставлять заведомо дублирующую запись), оно обязано идти туда же, где произойдёт запись |
| Фоновая обработка просроченных/заброшенных корзин (аналитика, ремаркетинг), TTL-очистка не в счёт — она серверная | **SECONDARY** | до 1–5 мин | не пользовательский путь, партия обрабатывается батчем, отставание не влияет на корректность |

**Почему у активной корзины почти всё — PRIMARY.** У `carts` (в отличие от `products` и
частично `orders`) частота обновлений на пользователя очень высокая, а окно между
записью и следующим чтением — секунды или меньше: «добавить товар» → тут же «показать
корзину». Это сценарий, наиболее уязвимый к отставанию репликации: SECONDARY,
отставший даже на доли секунды, с высокой вероятностью ещё не увидел последнюю запись,
и пользователь увидит корзину без только что добавленного товара. Бизнес-логика здесь
не про риск продажи или устаревшую сумму, а про доверие к интерфейсу — корзина,
«забывающая» товар, выглядит как баг и провоцирует повторные клики (что дополнительно
плодит нагрузку в пик).

## Проблема read-your-writes и как она решена

В трёх местах выше («страница подтверждения заказа», «просмотр корзины после
изменения», «check-then-act по статусу заказа») жёсткое требование — не «PRIMARY
всегда», а «эта конкретная операция чтения обязана видеть эту конкретную предыдущую
запись того же клиента». Формально это даёт два равноценных по корректности варианта:

1. **Читать с PRIMARY.** Простое решение по умолчанию для этого проекта: PRIMARY уже
   видел собственную запись по определению. Цена — не снимает нагрузку с PRIMARY для
   именно этих операций, но их доля в общем трафике `carts`/`orders` невелика по
   сравнению с листингом `products`.
2. **Читать с SECONDARY через causal consistency.** MongoDB-сессия
   (`client.start_session(causal_consistency=True)`) передаёт `operationTime` из
   предыдущей записи в последующее чтение через `afterClusterTime`; secondary, ещё не
   догнавший эту точку, будет ждать репликации (или отдаст ошибку по таймауту), но
   никогда не отдаст более старые данные. Это вариант для масштабирования, если доля
   read-your-writes операций вырастет настолько, что PRIMARY начнёт быть узким местом:

```python
async with await client.start_session(causal_consistency=True) as session:
    await db.carts.update_one(
        {"cart_key": cart_key, "status": "active"},
        {"$push": {"items": item}},
        session=session,
    )
    cart = await db.get_collection(
        "carts", read_preference=ReadPreference.SECONDARY_PREFERRED
    ).find_one({"cart_key": cart_key, "status": "active"}, session=session)
```

Для этого проекта на старте выбран вариант 1 (PRIMARY) как более простой и
предсказуемый; переход на вариант 2 стоит делать точечно для `carts`, если профилирование
покажет, что именно эти запросы формируют заметную долю нагрузки на PRIMARY шардов в пик распродажи.

## Сводная таблица

| Коллекция | На SECONDARY можно | Только PRIMARY | Типичное допустимое отставание |
|---|---|---|---|
| `products` | листинг, карточка, индикатор наличия, сквозной фильтр по цене | остаток и цена непосредственно при оформлении заказа | 5–10 c (до 30 c для нетаргетируемых запросов) |
| `orders` | история заказов, статус в личном кабинете (не сразу после создания), операционная аналитика | подтверждение сразу после оформления, check-then-act по статусу, идемпотентность платежа | 10–15 c (до 60 c для аналитики) |
| `carts` | фоновая обработка заброшенных корзин | активная корзина в текущей сессии, слияние при логине, проверка инварианта перед вставкой | секунды для фоновых задач; для активной корзины — 0 (PRIMARY или causal consistency) |

Общее правило, которое видно во всех трёх строках: SECONDARY допустим там, где
устаревшее чтение не участвует в следующем решении о записи и не является прямым
эхом действия, которое пользователь только что совершил. Как только чтение — это
«прочитать перед тем, как списать/отменить/подтвердить» или «показать результат
собственного только что сделанного действия», ответ — PRIMARY (или, как более
масштабируемая альтернатива для read-your-writes, causal consistency).

## Мониторинг допустимого отставания

Числа отставания в таблицах — не произвольные, а привязаны к порогу, за которым
SECONDARY нужно временно исключать из чтения. Это тот же `rs.status()` lag,
который уже фигурирует как индикатор в [задании 8](./task8.md#уровень-шарда-каждая-replica-set-шарда):

```javascript
rs.status().members
  .filter(m => m.stateStr === "SECONDARY")
  .map(m => ({ name: m.name, lagSeconds: (rs.status().date - m.optimeDate) / 1000 }));
```

Практический порог для этого проекта — если лаг конкретного SECONDARY превышает
верхнюю границу из таблицы для запросов, которые на него направлены (например, 10 c
для `products`/`orders`), драйверный `maxStalenessSeconds` здесь не поможет (минимум
90 c — см. [первый раздел](#как-читает-приложение-readpreference-и-его-границы)), поэтому
единственный практичный механизм — мониторинг и алерт на лаг с ручным/автоматическим
временным переключением чтения на PRIMARY (`readPreference: primaryPreferred`) для
затронутого шарда, пока отставание не выправится.
