## Как возникает горячий шард на этих данных

В [задании 7](./task7.md) коллекция `products` шардирована по `{ category: 1, _id: 1 }`
— диапазонная стратегия, где `category` служит префиксом ради таргетируемых запросов
витрины. У неё есть обратная сторона: балансировщик MongoDB выравнивает **число
чанков** между шардами, а не нагрузку на них. Если 70% запросов «чёрной пятницы» идёт
по категории `electronics`, а её диапазон целиком лежит в чанках одного-двух шардов,
кластер может быть идеально сбалансирован по количеству чанков и при этом иметь один
шард, забитый под 100% CPU, пока соседний простаивает.

Три независимых источника перекоса важны здесь одновременно:

1. **Перекос по объёму (storage skew)** — на шарде физически больше данных.
2. **Перекос по числу чанков (chunk skew)** — то, что балансировщик исправляет сам.
3. **Перекос по нагрузке (query/write skew)** — то, что балансировщик **не видит**:
   он не знает, что чанк `electronics` горячее чанка `books`, потому что чанки одного
   размера и одного количества документов могут получать совершенно разный трафик.

Именно (3) — причина инцидента в задании. Метрики и механизмы ниже отвечают на два
вопроса по отдельности: как узнать, что дисбаланс уже произошёл (мониторинг), и как
его снять, если автобалансировщик по своей природе на это не рассчитан (устранение).

## Метрики мониторинга

### Уровень кластера (mongos / config server)

| Метрика | Источник | Что показывает | Сигнал горячего шарда |
|---|---|---|---|
| `db.collection.getShardDistribution()` | `mongosh` | документов, средний размер, % от коллекции на каждый шард | доля одного шарда сильно выше `1/N` шардов |
| `sh.status()` → `chunks` по шарду | `mongosh` | число чанков на шард | не помогает напрямую (см. выше), но резкий перекос числа чанков — предвестник |
| `$currentOp` с `active: true`, агрегация по `shard` | `mongosh` / `db.currentOp()` | сколько операций сейчас выполняется на каждом шарде | один шард стабильно держит больше активных операций |
| `serverStatus().shardingStatistics` (на `mongos`) | `serverStatus` | счётчики миграций чанков: `countDonorMoveChunkStarted`, staleConfig-ошибки | всплеск миграций = балансировщик уже отреагировал на chunk skew |

### Уровень шарда (каждая replica set шарда)

| Метрика | Источник | Что показывает | Сигнал горячего шарда |
|---|---|---|---|
| `serverStatus().opcounters` (insert/query/update/delete) | `db.serverStatus()` на PRIMARY каждого шарда | RPS по типам операций | у одного шарда `opcounters` кратно выше, чем у остальных при равном числе чанков |
| `serverStatus().opLatencies` | `db.serverStatus()` | латентность чтения/записи в микросекундах | латентность растёт на одном шарде раньше, чем на остальных — ранний индикатор, до насыщения CPU |
| `serverStatus().globalLock.currentQueue` | `db.serverStatus()` | очередь операций, ждущих блокировку | устойчиво > 0 только на одном шарде |
| `serverStatus().wiredTiger.cache` (`bytes currently in the cache` / `maximum bytes configured`) | `db.serverStatus()` | давление на кеш WiredTiger | шард с горячей категорией вымывает кеш чаще — растёт `pages read into cache` |
| `db.serverStatus().connections.current` | `db.serverStatus()` | число активных подключений | непропорциональный рост на одном шарде при равномерном пуле подключений приложения |
| `rs.status()` → `members[].stateStr`, `optimeDate` lag | `rs.status()` на каждом узле группы | здоровье реплики, отставание SECONDARY | перегруженный PRIMARY чаще отстаёт по репликации, что видно как рост lag на его SECONDARY |
| OS-метрики: CPU, IOPS диска, network throughput контейнера | `docker stats` / Prometheus node-exporter | физическая нагрузка на хост шарда | самый прямой сигнал: один контейнер шарда заметно горячее остальных при равной аппаратной конфигурации |

### Уровень запроса (профайлер и explain)

| Инструмент | Что показывает |
|---|---|
| `db.setProfilingLevel(1, { slowms: 100 })` + `db.system.profile` | медленные операции с полем `planSummary`; по нему видно, ушёл ли запрос `SINGLE_SHARD` или разлетелся `SHARD_MERGE`-ом |
| `db.collection.explain("executionStats").find(...)` | число прочитанных/вернувшихся документов и участвовавшие шарды — тот же метод, что в разборе фильтра по цене в задании 7 |
| `mongostat` (агрегированный по всем узлам) | быстрый снимок `insert/query/update/delete/getmore` в реальном времени по каждому узлу кластера |

### Сборка в единый дашборд

Практическая схема для продакшена — экспортировать `serverStatus()` через
[`mongodb_exporter`](https://github.com/percona/mongodb_exporter) в Prometheus с
отдельным лейблом `shard` на каждой метрике, и в Grafana строить панели вида
«opcounters по шардам на одном графике». Перекос виден визуально: линия одного шарда
уходит вверх относительно остальных при одинаковом количестве чанков на этих же
шардах (второй график — `sh.status()` chunks per shard, снимается периодическим job'ом).

## Обнаружение: пороги и запрос-диагностика

Формальный критерий «шард горячий», который можно зашить в алерт:

```
opcounters(shard_i) / avg(opcounters по всем шардам) > 1.5   держится дольше 5 минут
```

Порог `1.5` и окно `5 минут` — отправная точка, а не константа: интервал должен
гасить кратковременные всплески на графике трафика, а не только шум мониторинга
(GC-паузы экспортёра, единичный медленный запрос). Значение калибруется по
исторической волатильности конкретной нагрузки в predev/staging.

Быстрая ручная диагностика при сработавшем алерте:

```javascript
// 1. Насколько неравномерно распределены документы категории
db.products.aggregate([
  { $group: { _id: "$category", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
]);

// 2. На каком шарде физически лежит горячая категория
db.products.getShardDistribution();

// 3. Что происходит на подозрительном шарде прямо сейчас
db.currentOp({ active: true, "ns": "shop.products" });

// 4. Подтверждение через профайлер: ушёл ли запрос на один шард
db.products.find({ category: "electronics", price: { $gte: 1000, $lte: 2000 } })
  .explain("executionStats").queryPlanner.winningPlan;
```

Шаг 1 и 2 вместе дают точный ответ на вопрос из инцидента: не «шард перегружен
абстрактно», а «шард 1 держит 70% чанков категории `electronics`, и именно туда
идёт трафик».

## Механизмы устранения дисбаланса

### 1. Штатный балансировщик чанков — необходимое, но не достаточное условие

Балансировщик MongoDB включён по умолчанию и перемещает чанки, выравнивая их
**количество** между шардами. Держать его настроенным правильно — обязательная
база, поверх которой уже решаются query/write skew:

```javascript
// статус и ручной запуск баланса
sh.getBalancerState();
sh.startBalancer();

// балансировка только в окне низкой нагрузки — не во время самой распродажи
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
);

// ограничение размера чанка (по умолчанию 128 МБ) — меньший чанк мигрирует быстрее
sh.setChunkSize?.(64) ?? db.settings.updateOne(
  { _id: "chunksize" }, { $set: { value: 64 } }, { upsert: true }
);
```

Важная оговорка: во время самой распродажи миграция чанков — дополнительная нагрузка
на донора и получателя (копирование данных, снапшоты oplog). Поэтому `activeWindow`
выше выставлен на ночное окно — балансировку в пик трафика включать не стоит, лучше
подготовить распределение заранее (см. пункт 3).

### 2. Zone sharding — развести горячую категорию физически

Прямое лекарство от найденной причины: если `electronics` систематически горячее
остальных категорий, её диапазон стоит закрепить за отдельной, более мощной группой
шардов, а не оставлять балансировщику решать это по количеству чанков.

```javascript
sh.addShardToZone("shard1", "HOT");
sh.addShardToZone("shard2", "STANDARD");

sh.updateZoneKeyRange(
  "shop.products",
  { category: "electronics", _id: MinKey },
  { category: "electronics", _id: MaxKey },
  "HOT"
);
```

Дальше зона `HOT` — обычная точка расширения: под неё добавляется третий шард
(`shard3`) с более производительным железом, и `updateZoneKeyRange` не трогается —
балансировщик сам разложит чанки `electronics` по всем шардам зоны `HOT`.

```javascript
sh.addShardToZone("shard3", "HOT");
```

Цена: зона перестаёт быть равномерной по определению — весь смысл в том, чтобы
изолировать нагрузку, а не размазать её. Это осознанный компромисс, а не побочный
эффект.

### 3. Упреждающее ручное разбиение и перемещение чанков перед пиком нагрузки

Балансировщик реагирует постфактум — по числу чанков, которое меняется медленнее,
чем растёт трафик распродажи. Перед плановым пиком (известная дата «чёрной пятницы»)
это разбиение можно сделать заранее, вручную, не дожидаясь автобаланса:

```javascript
// заранее раздробить диапазон electronics на более мелкие чанки —
// с мелкими чанками миграция синхронной командой не блокирует запись надолго
sh.splitAt("shop.products", { category: "electronics", _id: ObjectId("...") });

// и явно раскидать получившиеся чанки по разным шардам
sh.moveChunk(
  "shop.products",
  { category: "electronics", _id: ObjectId("...") },
  "shard2"
);
```

### 4. Приложенческий уровень: шардирование по времени/суффиксу для пиковых категорий

Если даже разбиение диапазона `electronics` не даёт нужной параллельности (весь
трафик распродажи идёт по одному и тому же узкому под-диапазону — например, топ-10
товаров дня распродажи), проблема уже не в физическом размещении чанков, а в самом
шард-ключе: `{ category, _id }` не распределяет **топовые** товары. В этом случае
практика — «шардирование через суффикс» на уровне приложения: искусственно
расширить кардинальность ключа для горячих документов.

```javascript
// вместо одного документа товара с category: "electronics" —
// логическое дробление горячих SKU на N теневых партиций для операций записи
// (например, атомарного списания остатка), которые затем агрегируются приложением
{ category: "electronics", _id: ObjectId("..."), stock_partition: 3 }  // 0..N-1
```

Это не механизм MongoDB, а паттерн работы с ним — применяется точечно, только для
подтверждённо горячих SKU, а не для всей категории, потому что усложняет чтение
(нужна агрегация по партициям при подсчёте остатка).

## Что не лечится автобалансировщиком

Явно фиксирую границу применимости штатного баланса, чтобы не создавать ложных
ожиданий:

- **Балансировщик не видит нагрузку**, только число чанков — задание уже показало
  почему: 70% запросов на одну категорию при формально ровном распределении чанков.
- **Балансировщик не работает во время активной миграции больших чанков** без
  ручного `sh.setChunkSize` — крупные чанки (близко к 128 МБ) мигрируют медленно и
  создают собственную нагрузку в момент, когда кластер и так под давлением.
- **Балансировщик не меняет шард-ключ.** Если сам ключ (как в пункте 4 выше) не
  дробит горячие документы, никакая миграция чанков не поможет — нужно либо
  расширять кардинальность на уровне приложения, либо резать зону под нагрузку
  (пункт 2).

Отсюда практический вывод: метрики из первого раздела должны алертить не только на
общую нехватку ресурсов, а конкретно на дисбаланс *между* шардами при относительно
ровном распределении чанков — это единственный надёжный сигнал, что дело именно в
горячей категории, а не в общем росте трафика.

## Сводная таблица

| Механизм | Когда применять | Автоматический? |
|---|---|---|
| Штатный балансировщик + `activeWindow` | база всегда, окно — вне пиковых часов | да |
| Zone sharding по категории | категория систематически горячее остальных | нет, требует ручной настройки зон один раз |
